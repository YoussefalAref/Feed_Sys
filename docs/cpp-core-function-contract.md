# C++ Core Function Contract

This is the handoff file for the C++ team. It follows the current team plan:
the project is a C++ data-structures project first, and Python/FastAPI is only
the HTTP and pybind wrapper layer.

## Core Rule

Most business and recommendation logic belongs in C++.

Python/FastAPI should only:

- receive HTTP requests
- validate/serialize JSON
- call pybind functions
- handle external payment provider calls and secrets
- optionally persist/load snapshots if the demo uses PostgreSQL

C++ should own:

- users/items lookup through custom `HashMap`
- recent interactions through custom `Queue`
- item ranking through custom `MaxHeap`
- related-product similarity through custom `Graph`
- user activity score and level updates
- cart state
- dashboard stats
- recommendation scoring

## Team Plan Clusters

Keep the same three clusters from the plan so the team does not need to
reorganize their work:

1. Auth and Users
2. Products, Cart, and Dashboard
3. Interactions and Recommendations

## C++ Data Structures To Use

| Data structure | Required role |
|---|---|
| `HashMap<int, User>` | user lookup, auth lookup support, user activity updates |
| `HashMap<int, Item>` | item lookup, CRUD, stock/popularity updates |
| `HashMap<int, Cart>` or `HashMap<int, CartItem[]>` | cart by user id |
| `Queue<Interaction>` | append every view/click/cart/purchase event in arrival order |
| `MaxHeap<ItemScore>` | trending products and top-K recommendation candidates |
| `Graph<int>` | item-to-item/category similarity and related products |

## DTO Types

Keep these DTO names stable because pybind will expose/convert them.

```cpp
#pragma once

#include <string>
#include <vector>

enum InteractionType {
    VIEW,
    CLICK,
    ADD_TO_CART,
    PURCHASE
};

struct UserInput {
    std::string name;
    std::string email;
    std::string password;
    std::string category;
    std::string region;
};

struct UserDTO {
    int id;
    std::string name;
    std::string email;
    std::string category;
    double score;
    std::string region;
    int activity_score;
    std::string level; // "Normal" | "Active" | "VIP"
};

struct AuthResult {
    bool success;
    std::string error;
    UserDTO user;
    std::string token;
};

struct ProductInput {
    std::string name;
    double price;
    std::string category;
    int stock;
    std::string image;
    std::string description;
    double popularity_score;
};

struct ProductDTO {
    int id;
    std::string name;
    double price;
    std::string category;
    double popularity_score;
    int stock;
    std::string image;
    std::string description;
};

struct InteractionDTO {
    int id;
    int user_id;
    int item_id;
    std::string type;      // "view" | "click" | "cart" | "purchase"
    std::string timestamp; // ISO string supplied by Python or generated by C++
};

struct CartItemDTO {
    int user_id;
    int item_id;
    int quantity;
    ProductDTO product;
};

struct CheckoutItemDTO {
    int item_id;
    std::string name;
    double price;
    int quantity;
};

struct CheckoutDraft {
    bool success;
    std::string error;
    int user_id;
    double total;
    std::vector<CheckoutItemDTO> items;
};

struct CheckoutResult {
    bool success;
    std::string error;
    int purchased;
    int user_id;
};

struct DashboardStats {
    int totalProducts;
    int totalUsers;
    int totalInteractions;
    std::string mostPopularCategory;
};

struct RecommendationDTO {
    ProductDTO product;
    double recommendation_score;
    std::string reason;
};

struct RelatedProductDTO {
    ProductDTO product;
    double similarity_score;
};
```

## Core Lifecycle Functions

These functions let Python load seed/database data into the C++ engine without
Python owning the logic.

```cpp
void reset_core();

void load_users(const std::vector<UserDTO>& users);
void load_products(const std::vector<ProductDTO>& products);
void load_interactions(const std::vector<InteractionDTO>& interactions);
void load_cart(const std::vector<CartItemDTO>& cart_items);

bool is_core_ready();
```

Data-structure impact:

- `load_users` fills `HashMap<int, User>`.
- `load_products` fills `HashMap<int, Item>`, rebuilds `MaxHeap`, and rebuilds
  graph nodes.
- `load_interactions` fills the `Queue<Interaction>` and replays interaction
  score effects if needed.
- `load_cart` fills cart storage by user id.

```cpp
    int user_id,
    int item_id
);

CheckoutDraft create_checkout_draft(int user_id);

DashboardStats get_dashboard_stats();
```

Why checkout is split:

- C++ owns cart state and creates the checkout draft.
- Python owns Paymob/Fawry network calls and stores payment attempts.
- After payment is paid, Python calls `finalize_paid_checkout(user_id)`.
- C++ then records purchase interactions in the queue, updates item/user
  scores, and clears the user's cart.

Helper functions that can remain internal C++:

```cpp

std::string most_popular_category();
```

Data structures:

- `HashMap<int, Item>` for product CRUD and lookup.
- `HashMap<int, Cart>` for cart by user.
- `MaxHeap<ItemScore>` for top products and dashboard/trending support.
- `HashMap<std::string, double>` or equivalent custom map for category score
  aggregation in dashboard stats.

## Cluster 3: Interactions And Recommendations

Interactions must be stored in C++ queue state.

```cpp
InteractionDTO record_interaction(
    int user_id,
    int item_id,
    const std::string& interaction_type
);

std::vector<InteractionDTO> get_recent_interactions(int limit);

std::vector<RecommendationDTO> get_recommendations(
    int user_id,
    int limit
);

std::vector<RelatedProductDTO> get_related_products(
    int item_id,
    int limit
);

std::vector<ProductDTO> get_trending(int limit);
```

Interaction mapping:

```text
"view"     -> VIEW        -> +1 item popularity, +1 user activity
"click"    -> CLICK       -> +2 item popularity, +2 user activity
"cart"     -> ADD_TO_CART -> +5 item popularity, +5 user activity
"purchase" -> PURCHASE    -> +10 item popularity, +10 user activity
```

Required `record_interaction` behavior:

1. Validate user exists in `HashMap<int, User>`.
2. Validate item exists in `HashMap<int, Item>`.
3. Create `Interaction`.
4. Enqueue it into `Queue<Interaction>`.
5. Update item popularity score.
6. Update user activity score and level.
7. Update/rebuild affected heap position.
8. Return `InteractionDTO`.

Helper functions that can remain internal C++:

```cpp
InteractionType parse_interaction_type(const std::string& type);
std::string interaction_type_to_string(InteractionType type);
int interaction_weight(InteractionType type);
int generate_interaction_id();
long current_timestamp();

std::vector<int> get_user_recent_item_ids(int user_id, int limit);
double graph_similarity_score(int source_item_id, int candidate_item_id);
double category_interest_boost(int user_id, const std::string& category);
double recommendation_score(int user_id, int item_id);
```

Data structures:

- `Queue<Interaction>` for recent events.
- `HashMap<int, User>` for user activity updates.
- `HashMap<int, Item>` for item popularity updates.
- `MaxHeap<ItemScore>` for trending and candidate ranking.
- `Graph<int>` for related item traversal.

## Acceptance Checklist

- Core builds independently before pybind.
- Interactions are actually stored in the C++ queue.
- `record_interaction` updates queue, user score, item score, and heap ranking.
- Product CRUD updates the C++ item HashMap and heap/graph state.
- Cart operations update C++ cart state.
- Recommendations use heap + graph + recent queue/user history.
- Dashboard stats use C++ state, not Python counting.
- Pybind exposes the exact names above.
- Python can call every exported function and convert returned DTOs to JSON.
- Frontend service function names do not change.
